# Paper L1 — A Knowledge-Graph Schema for Unity Projects

**Research question (per spec §1.8):** What is the minimal graph schema that
captures enough Unity-specific semantics to make LLM tasks correct, and how
does this schema differ structurally from a standard code dependency graph?

## Thesis

Unity projects are not code graphs. They are **code-plus-scene** graphs
where scene YAML carries data that overrides, augments, or invalidates
conclusions drawn from source alone. A schema that captures this duality
with a small set of node/edge types (≤ 10) is sufficient to close the
scene-code gap on typical Unity tasks, and structurally distinct from a
standard code graph in three specific ways.

## Claimed contribution

1. A semantic graph schema for Unity projects with 8 node types and 11
   edge types (v1.1, this release), designed from the Unity YAML format
   and the six pre-seeded failure patterns in the project spec §3.5.
2. Empirical comparison to code-only dependency graphs: what percentage
   of scene-dependent tasks a pure code graph can answer (≈ 0, by
   construction of the spec-seeded failure patterns) vs the graph-augmented
   schema.
3. A scalability characterization: build time, MCP tool response time, and
   graph size across three real Unity projects spanning 130 to 1,519
   scripts.

## Evidence

All artifacts generated by this package:

- `src/unitygraph/build/graph.py` — the schema definition (node + edge
  Literals + id generators).
- `UnityGraph_Project_Spec.md` §1.4 — the minimal required semantic
  content, motivating which nodes/edges must be expressible.
- I2 benchmark data (repo history `f0e8514`, `a91c92f`): build-time,
  skip-rate, and node-count statistics across Indian-Bike-Gangster-3D
  (1,335 nodes), clash.io (6,273 nodes), Graudation-Saga (72,564 nodes).
- MCP tool response times from `evals/perf/measure_tools.py`: median
  <50ms even on the 72,564-node Graudation-Saga graph.

## Structural distinctions from a standard code graph

1. **Attachment (``attached_to``) edges carry payloads.** Scene-set
   Inspector values live on the edge between a Script node and its
   GameObject — not on the Script node. Two graphs sharing the same Script
   definition can have materially different runtime behavior because of
   these edge payloads. A standard code graph has no edge payloads; its
   edges are structural (inherits, calls).
2. **Duality nodes.** A Script node is simultaneously a type (code) and an
   asset (referenced by `MonoBehaviour.m_Script.guid`). A standard code
   graph conflates these or omits the asset identity entirely.
3. **UnityEvent connections are edges, not call-graph facts.** A
   ``subscribes_to`` edge between two Script nodes typically has no
   supporting evidence in source — the wiring lives in scene YAML. Pure
   static analysis misses it.
